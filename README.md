# 쿠팡 상품 소싱 분석 프로그램 (MVP 1단계)

쿠팡 카테고리를 선택하고, **Chrome에 실제로 렌더링된** 쿠팡 페이지의 상품 정보를 수집해서,
**리뷰수 기반 예상 판매량**으로 소싱 후보 상품을 찾는 도구입니다.

> ⚠️ 이 프로그램이 계산하는 값은 **예상 판매량(estimated sales)** 입니다. 실제 판매량이 아닙니다.
> `예상 판매량 = 리뷰수 × review_sales_multiplier (기본 20, 화면에서 변경 가능)`

## 구성

| 모듈 | 스택 | 설명 |
|---|---|---|
| `backend/` | Python 3.11, FastAPI, SQLAlchemy 2.x, SQLite | API + DB + 필터/계산 |
| `frontend/` | Next.js(App Router), TypeScript, Tailwind CSS, shadcn/ui 스타일 | 다크모드 분석 대시보드 |
| `extension/` | Manifest V3, TypeScript | 현재 Chrome 페이지 DOM에서 상품 정보 추출 |

초보자 가이드: [시작하기.md](시작하기.md)
설계 문서: [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md)

## 실행 방법

### 1) 백엔드 (터미널 1)

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

python -m app.cli init-db                                # 테이블 생성 + 기본 설정
python -m app.cli import-categories data/categories_sample.json
python -m app.cli show-tree                              # 카테고리 트리 확인

uvicorn app.main:app --reload --port 8000                # http://localhost:8000/docs
```

### 2) 프론트엔드 (터미널 2)

```bash
cd frontend
npm install
npm run dev                                              # http://localhost:3000
```

백엔드 주소가 다르면 `frontend/.env.local` 에 `NEXT_PUBLIC_API_BASE_URL=http://localhost:8000`.

### 3) Chrome 확장 (터미널 3)

```bash
cd extension
npm install
npm run build                                            # → extension/dist
```

1. Chrome에서 `chrome://extensions` 열기
2. 우측 상단 **개발자 모드** 켜기
3. **압축해제된 확장 프로그램을 로드** → `extension/dist` 폴더 선택

### 4) 사용 흐름 — 대시보드에서 클릭 2번

크롬 확장은 설치만 해 두면 됩니다. popup 을 열 일이 없습니다 (대시보드가 확장을 직접 구동합니다.
「실행」 패널 오른쪽에 **● 확장 연결됨** 이 보이면 준비된 것입니다).

0. (처음 한 번) 카테고리 패널의 **[쿠팡 카테고리 가져오기]** → 쿠팡 첫 화면 메뉴에서 전체 트리를 읽어옵니다
1. 카테고리를 **체크** (상위 카테고리를 체크하면 하위 전체가 포함됩니다), 조건과 페이지 수·상세 확인 수 설정
2. **[소싱 시작]**

이후는 자동입니다. 확장이 탭 하나를 열어

- **1단계 목록** — 체크한 카테고리와 그 아래 전부(중간 단계 포함)를 **판매량순** 목록 페이지로 N페이지씩 방문해 저장.
  주소의 `sorter=saleCountDesc` 만 믿지 않고, 페이지에 뜬 정렬 컨트롤을 읽어 판매량순이 아니면 화면의
  "판매량순"을 직접 눌러 맞춘 뒤 읽습니다. 결과는 실행 패널 "방금:" 줄에 `정렬: … · 읽음 N개 · 저장 M개`로 남습니다.
  페이지 좌측 메뉴에서 **트리에 없던 하위 카테고리를 발견하면 트리와 이번 스캔 대상에 자동 추가**
  (쿠팡 첫 화면 메뉴에는 하위가 일부만 실려 있기 때문. 한 번의 스캔에서 최대 300페이지)
- **2단계 상세** — 1차 조건을 통과했지만 30일 리뷰수를 아직 못 잰 상품을 누적 리뷰 많은 순으로 상세 페이지에
  들어가 리뷰를 최신순으로 넘기며 **최근 30일 리뷰수**를 세고, **"한 달간 N명 이상 구매"** 문구도 함께 저장

대시보드 「실행」 패널에 진행률(`수집 중 · 2단계 상세 12/58 · 현재: 상품명`)이 실시간으로 표시되고,
끝나면 **[엑셀로 내려받기]**로 조건 통과 상품을 CSV(엑셀에서 바로 열림, UTF-8 BOM)로 저장합니다.
일시정지/재개/중단도 대시보드에서 합니다. 실패가 생기면 「실행」 패널에 **최근 실패 사유**가 그대로 표시됩니다.
뭔가 안 되면 「실행」 패널 맨 아래 **[문제 보고서 복사]** → 채팅에 붙여넣기. 서버 기록·최근 수집 결과·버전이
한 번에 담깁니다 (`GET /api/diagnostics`). 목록 페이지에서 상품을 읽었는데 저장이 0건이면 그 사유가 실패로 기록됩니다.
(확장 popup 은 대시보드 없이 쓰거나 문제를 진단할 때만 필요합니다.)

엑셀 컬럼: 판정 · 상품명 · 카테고리 · 30일 리뷰수 · 30일 예상판매량 · 30일 예상매출 · 한 달 구매(쿠팡 표시) ·
가격 · 누적 리뷰수 · 누적 예상판매량 · 평점 · 배송 · 측정 방식 · 신뢰도 · 상품 ID · 상품 링크 · 최근 수집

결과 표 위의 탭: **조건 통과 / 전체 / 미달 / 30일 미측정**. 조건을 설정하면 기본으로 통과 상품만 보입니다.
통과가 0건이면 표 안에 **조건별 탈락 수**("한 달 구매 문구 없음 N개", "30일 미측정 N개" …)가 나와 어느 조건이 걸렀는지 보입니다.
카테고리 검색창은 이름뿐 아니라 쿠팡 주소의 `categoryId` 숫자로도 찾습니다.

**이번 검색 / 누적 전체** — 표와 KPI는 기본으로 마지막 [소싱 시작]에서 훑은 상품만 보여줍니다(검색을 새로 하면
이전 결과는 화면에서 사라짐). 이전 상품은 DB에 남아 있어(리뷰수 변화 추적·보관함용) "누적 전체"로 볼 수 있습니다.

**보관함** — 결과 표의 ☆ 또는 [통과 상품 보관]으로 골라 두면 검색과 무관하게 남습니다. 헤더의 [보관함] 탭에서
저장 당시 숫자(30일 리뷰·예상판매·예상매출·한 달 구매·가격)와 현재 숫자를 나란히 보고, 메모를 적고, 엑셀로 내려받습니다.

> **사람 속도로 움직입니다.** 목록 4~7초, 상세 6~10초 간격(무작위), 10개마다 20~35초 휴식, 리뷰 넘김은
> 상품당 최대 10페이지, 기본 상세 확인 30개(약 5분). 실제로 상세 50개를 2.5초 간격으로 열자 쿠팡(Akamai)이
> "Access Denied"로 막았습니다. 차단 화면이 뜨면 **우회하지 않고 즉시 멈추고** 실행 패널에
> "30분~1시간 뒤 [재개]"를 안내합니다. 그 밖의 실패는 그 대상만 실패로 기록하고 계속하며, 5회 연속 실패하면 멈춥니다.

## 한 달 판매량 파악하기

핵심 지표는 **최근 30일 리뷰수 → 30일 예상 판매량(× 배수, 기본 20) → 30일 예상매출(× 가격)** 입니다.
표는 이 순서로 보여주고 기본 정렬은 30일 예상매출 많은순, 「소싱 기준」 버튼(월 500/1,000/3,000개)은
30일 예상 판매량 기준입니다. 누적 리뷰수 × 배수는 참고용으로만 남겨 두었습니다(엑셀에만 나옵니다).

30일 리뷰수는 상품 상세 페이지의 리뷰를 **최신순으로 정렬해 30일보다 오래된 리뷰가 나올 때까지
[다음 페이지]를 넘기며** 셉니다(자동 스캔 2단계, 상품당 최대 20페이지). 그 안에 못 덮으면 표본 기간으로
추정하고 신뢰도를 낮춥니다. 같은 방문에서 쿠팡의 "한 달간 N명 구매" 문구도 함께 저장해 **2차 확인**에 씁니다.

### 2차 확인 — 쿠팡이 표시하는 "한 달 구매" (실제 데이터)

쿠팡은 **상품 상세 페이지**에 이런 문구를 붙여 줍니다.

> ⭐ 4.5 · 13,633개 상품평 · 👍 **한 달간 3,000명 이상 구매했어요**

**우리가 추정한 값이 아니라 쿠팡이 계산해 표시한 실제 판매 데이터**입니다.
확장이 이 문구를 읽어 `monthly_purchase_count` 로 저장하고, 소싱 조건의 1순위 근거로 씁니다.

> ⚠️ **이 문구는 카테고리·검색 목록 페이지에는 없습니다. 상품 상세 페이지에만 있습니다.**
> 그래서 아래 2단계 워크플로가 필요합니다.

### 2단계 소싱 워크플로

```
1단계  카테고리 페이지 수집          2,994개
       └ 가격·리뷰수·평점·배송으로 1차 필터
                                    ↓
                                   80개
2단계  후보 상세 페이지 방문
       └ "한 달간 N명 이상 구매" 확인
                                    ↓
       월 1,000개 이상 최종 후보     12개
```

**[소싱 시작] 한 번이면 두 단계가 자동으로 이어집니다.** 목록 수집이 끝나면 1차 조건을 통과했지만
구매 문구가 없는 상품을 리뷰 많은 순으로 「상세 확인 상품 수」만큼 골라 상세 페이지를 순서대로 방문합니다.
상세 페이지에서는 리뷰를 최신순으로 넘기며 30일 리뷰수도 함께 셉니다.

수동으로 보완할 때 쓰는 장치 두 가지:

1. **확장 popup의 `상품 페이지 열면 자동 수집` 체크** — 직접 연 상품 페이지도 저장됩니다.
2. **대시보드의 `상세 확인 필요` 버튼** — 아직 구매 문구를 확인하지 못한 상품만 보여줍니다.

**「소싱 기준」 버튼은 두 신호 중 하나만 넘으면 통과입니다** — 쿠팡의 "한 달간 N명 이상 구매" 문구 **또는**
30일 리뷰수 × 배수 추정치. 리뷰 비율이 낮은 상품(잘 팔리는데 리뷰가 적은 것)은 문구로, 문구가 없는 상품은
추정치로 잡힙니다. 처음 켜면 **월 500개 이상 · 가격 9,000~40,000원**이 기본으로 들어 있습니다.

| 버튼 | 조건 (배수 20 기준) |
|---|---|
| 월 500개 이상 | 문구 ≥ 500명 **또는** 30일 예상 판매량 ≥ 500(= 30일 리뷰 25건) |
| 월 1,000개 이상 | 문구 ≥ 1,000명 **또는** 30일 예상 판매량 ≥ 1,000(= 30일 리뷰 50건) |
| 월 3,000개 이상 | 문구 ≥ 3,000명 **또는** 30일 예상 판매량 ≥ 3,000(= 30일 리뷰 150건) |

상세 방문 후보를 고를 때 **누적 리뷰가 기준÷배수보다 적은 상품은 건너뜁니다**(절대 통과할 수 없으므로).
방문 수가 줄어 차단 위험도 줍니다.

주의할 점 두 가지 (화면에도 표시됩니다):
- 단위가 **"명"**이면 구매자 수입니다. 실제 판매 **수량**은 그 이상입니다.
- **"이상"이 붙은 구간값**입니다. "3,000명 이상" = 3,000~4,999 사이입니다.

→ 둘 다 **과소 추정** 방향이라, "월 1,000개 이상" 같은 하한 조건에는 안전합니다.

### 핵심 — 최근 30일 리뷰수 기반 추정

문구가 붙지 않은 상품은 리뷰수로 추정합니다.

**쿠팡은 "최근 1달 리뷰수"를 화면 어디에도 표시하지 않습니다.**
상품 카드와 상세 페이지에 보이는 리뷰수는 전부 **누적** 리뷰수입니다.
따라서 최근 30일 리뷰수는 DOM에서 읽는 것이 아니라 **유도**해야 하며,
이 프로그램은 두 가지 방법을 함께 제공합니다.

| 방법 | 원리 | 정확도 | 대상 | 언제 쓸 수 있나 |
|---|---|---|---|---|
| **① 리뷰 날짜 분석** | 상세 페이지 리뷰를 최신순 정렬 → 화면에 렌더된 리뷰의 **작성일**을 직접 셈 | 실측 (렌더된 범위 내) | 상품 1건씩 | **바로** |
| **② 리뷰수 변화 추적** | 수집할 때마다 누적 리뷰수 스냅샷 저장 → `이번 값 − 30일 전 값` | 실측 (완전) | 카테고리 전체 수천 건 | 재수집이 쌓인 뒤 |

`최근 30일 예상 판매량 = 최근 30일 리뷰수 × 배수`

두 값이 모두 있으면 **관측 구간이 길고 환산이 아닌 쪽**을 채택합니다.
어느 쪽으로도 구할 수 없으면 `NULL`로 두고 화면에 `-` 로 표시합니다. **임의 값을 만들지 않습니다.**

### ① 리뷰 날짜 분석 사용법 (즉시)

쿠팡 리뷰는 **로그인 없이** 볼 수 있고 최신순 정렬도 됩니다.

1. 쿠팡 **상품 상세 페이지**를 엽니다.
2. 리뷰 영역에서 정렬을 **최신순**으로 바꿉니다. (베스트순이면 표본이 왜곡됩니다 — 확장이 경고합니다)
3. **30일보다 오래된 리뷰가 나올 때까지 리뷰 페이지를 넘깁니다.**
   쿠팡 리뷰 목록은 페이지를 넘기면 이전 리뷰가 화면에서 사라지지만,
   **확장이 넘기는 동안 자동으로 리뷰를 누적**합니다(중복 제거 포함).
4. 확장 아이콘 → **[리뷰 날짜 분석]** 클릭.

동작 예 (페이지당 5건):

| | 누적 표본 | 결과 |
|---|---|---|
| 1페이지 | 5건 (최근 10일) | 최근 30일 리뷰 **15건 (추정)** |
| 2페이지 | 10건 (최근 27일) | 최근 30일 리뷰 **11건 (추정)** |
| 3페이지 | 15건 (30일 경계 넘음) | 최근 30일 리뷰 **10건 (실측)** ✅ |

- 30일보다 오래된 리뷰까지 읽었다면 → **실측**
- 읽은 리뷰가 전부 30일 안이라면 → **추정**: 리뷰 속도(표본 ÷ 표본 기간)로 30일치를 환산하고 `추정` 배지를 붙입니다. 페이지를 더 넘긴 뒤 다시 누르면 실측으로 바뀝니다.
- 다른 상품으로 이동하면 누적이 자동 초기화됩니다. popup의 **[누적 초기화]** 로 직접 비울 수도 있습니다.

> 확장은 **사용자가 화면에 띄운 리뷰만** 읽습니다. 다음 페이지를 자동으로 요청하지 않습니다.

### ② 리뷰수 변화 추적 사용법 (자동, 전체 상품)

같은 카테고리/검색 페이지를 **며칠 간격으로 다시 수집**하기만 하면 됩니다.
수집할 때마다 누적 리뷰수가 `review_snapshots` 테이블에 쌓이고, 백엔드가 자동으로 차분을 계산합니다.

- 30일 이상 간격의 스냅샷이 있으면 → **실측**
- 그보다 짧으면 → 30일로 환산해 **추정**으로 표시 (예: 10일간 20건 → 30일 60건)
- 간격이 하루 미만이면 오차가 커서 계산하지 않습니다.
- 리뷰가 줄어든 경우(삭제 등)는 0으로 처리합니다. 음수를 만들지 않습니다.

### 화면에서 보이는 것

- 결과 테이블: `한 달 구매`(쿠팡 실제 데이터, 초록색) / `30일 리뷰` / `30일 예상판매`
  (미측정은 `-`, 환산값은 `추정` 배지, 툴팁에 원문 문구·측정 방식·표본 크기·신뢰도)
- 상단 KPI: `구매수 확보` — 쿠팡 구매 문구를 확보한 상품 수
- 왼쪽 조건: `한 달 구매`, `최근 30일 리뷰수`, `최근 30일 예상 판매량` 범위 (측정된 상품만 통과)
- 정렬: `한 달 구매 많은순/적은순`, `최근 30일 판매량 많은순/적은순`, `최근 30일 리뷰 많은순/적은순`

### 측정 신뢰도

리뷰 기반 추정값에는 신뢰도(`high`/`medium`/`low`)가 붙습니다.
예를 들어 1일 간격 재수집으로 리뷰가 1건 늘면 30일 환산 시 30건(=600개)으로 튑니다.
이런 값이 소싱 후보에 섞이지 않도록 표본 크기와 관측 구간으로 판정하며,
API에서 `min_confidence=medium` 으로 걸러낼 수 있습니다.

## 카테고리 트리 채우기 — 버튼 한 번

카테고리 목록을 직접 만들거나 올릴 필요가 없습니다. 대시보드 카테고리 패널의
**[쿠팡 카테고리 가져오기]**(확장 popup 에도 같은 버튼이 있습니다)를 누르면 확장이 쿠팡 첫 화면(www.coupang.com)을
백그라운드 탭으로 잠깐 열어 **전체 카테고리 메뉴**에 렌더링된 링크를 읽고, 계층까지 그대로 등록한 뒤 탭을 닫습니다.
트리가 바로 나타나고, 그때부터는 체크만 하면 됩니다.

- 계층은 클래스명이 아니라 메뉴의 **DOM 중첩**으로 판단합니다 (`extension/src/parsers/coupang_category_parser.ts`).
  쿠팡이 메뉴 디자인을 바꿔도 링크가 중첩돼 있기만 하면 동작합니다.
- 화면에 있는 카테고리만 등록합니다. 코드나 이름을 지어내지 않습니다.
- 쿠팡 첫 화면 메뉴에는 하위 카테고리가 **일부만** 실려 있습니다. 나머지는 자동 스캔이 카테고리 페이지에
  들어갔을 때 **좌측 메뉴에서 발견해 트리에 추가하고, 그 하위 페이지도 이어서 스캔**합니다.
  즉 상위 하나만 체크해도 실제 하위 전부가 돌아갑니다. 쓰면 쓸수록 트리가 깊어집니다.
- 한 카테고리 코드는 트리에서 한 곳에만 놓입니다. 쿠팡의 기획 카테고리(예: "1인가구 주방용품")처럼
  같은 코드가 여러 메뉴에 나오면 마지막에 방문한 페이지의 부모 아래로 옮겨집니다.
- 다시 눌러도 중복되지 않습니다 (코드 기준 갱신).

메뉴를 찾지 못하면 popup에 "카테고리 링크를 N개밖에 찾지 못했습니다"가 뜹니다. 그때는 쿠팡 첫 화면을
직접 열고 '카테고리' 메뉴를 펼친 상태에서 다시 누르거나, [진단 정보 복사] 결과를 보내주세요.

파일로 올리는 방법도 남아 있습니다 (JSON/CSV, 컬럼: `category_code, category_name, parent_category_code, depth, category_url`):
`POST /api/categories/import/file` 또는 `python -m app.cli import-categories <파일>`.
부모를 적지 않은 행은 기존 부모 연결을 유지합니다.

## 상품 데이터는 DOM이 아니라 페이지 데이터에서 읽습니다

쿠팡 목록/검색 페이지는 Next.js로 만들어져 있고, 상품 데이터를 화면에 그리기 전에
아래 형태로 페이지에 함께 실어 보냅니다.

```js
self.__next_f.push([1, "...{\"legacyProductId\":8133306304,
  \"imageAndTitleArea\":{\"title\":\"...\"},
  \"priceArea\":{\"i18nSalesPrice\":{\"amount\":\"9800\"}},
  \"reviewArea\":{\"ratingCount\":18,\"ratingAverage\":4},
  \"deliveryUnificationBadgeArea\":{...\"badgeId\":\"ROCKET_MERCHANT\"}}..."])
```

**이걸 1순위로 읽습니다.** DOM에서 클래스명으로 긁는 것보다 정확하고,
쿠팡이 화면을 개편해도 이 데이터 구조는 잘 바뀌지 않습니다.

| | DOM 파싱 | 페이지 데이터 |
|---|---|---|
| 상품 ID | `data-id="0"` 같은 함정 있음 | `legacyProductId` 정확 |
| 가격 | `"13,900"` 텍스트 파싱 | `"9800"` 숫자 |
| 리뷰수·평점 | `"( 590 )"` 텍스트 파싱 | `590`, `4.5` 숫자 |
| 배송 방식 | alt 없는 배지 이미지 추정 | `ROCKET_MERCHANT` 코드 |
| 카테고리명 | selector 의존 | 페이로드에 포함 |

페이지 데이터를 찾지 못하면 아래 DOM 파싱으로 넘어갑니다.

## 쿠팡이 화면을 개편해도 동작하는 이유

쿠팡은 개편 때마다 클래스명을 통째로 바꿉니다
(`search-product` → `ProductUnit_productUnit__해시` → `twc-*` 유틸리티 클래스).
그래서 파서는 클래스명에만 의존하지 않고 **구조와 값의 형태**를 함께 씁니다.

| 대상 | 1순위 | 2순위 (개편 대비) |
|---|---|---|
| **전체 상품 목록** | **`__next_f` 페이지 데이터 (1순위)** | 아래 DOM 경로들 |
| 상품 카드 | 알려진 클래스 selector | **`a[href*="/vp/products/"]` 링크에서 위로 역추적** |
| 상품 ID | **상품 URL의 `/vp/products/{id}`** | data-* 속성 (6자리 이상 숫자만) |
| 상품명 | 클래스 selector | 썸네일 `img[alt]` |
| 가격 | 클래스 selector | **`13,900` 형태 + 옆에 `원`이 있는 요소** |
| 리뷰수 | 클래스 selector | **`(1,234)` 형태의 텍스트** |
| 평점 | 클래스 selector | **`style="width:94%"` → 4.7 환산** |
| 배송 | 배지 selector | 배지 `img`의 alt·**파일명**(`logoRocketMerchant`) → 카드의 짧은 라벨 |
| 리뷰 카드 | 클래스 selector | **`data-review-id` 앵커** |
| 리뷰 작성일 | 클래스 selector | **전체 텍스트가 날짜인 요소** |
| 한 달 구매 | 클래스 selector | **"한 달간 N명 이상 구매" 문구 자체** |

클래스명이 **하나도 맞지 않는** 전면 개편 상황을 가정한 테스트가 포함되어 있습니다
(`extension/src/tests/list-redesign.test.ts`, `review-parser-twc.test.ts`).

## 쿠팡 화면이 바뀌어 상품/리뷰가 감지되지 않을 때

### 1단계 — 진단 정보 뽑기

**방법 A: 확장 popup (권장)**

확장 아이콘 → **[진단 정보 복사]** → 클립보드에 리포트가 복사됩니다.

**방법 B: DevTools 콘솔 (확장 설치 없이)**

1. 쿠팡 페이지에서 `F12` → **Console** 탭
2. Chrome이 붙여넣기를 막으면 `allow pasting` 을 입력하고 Enter
3. 아래 파일 내용을 **전부 복사**해서 콘솔에 붙여넣고 Enter
   - 목록 페이지: [`tools/list-page-dump.js`](tools/list-page-dump.js) (빌드 불필요)
   - 상세 페이지: `extension/dist/selector-dump.js` (`npm run build` 필요, 개인정보 마스킹 포함)
4. 결과가 클립보드에 자동 복사됩니다

**방법 C: 수동**

리뷰 하나에서 **우클릭 → 검사** → Elements 패널에서 감싸는 `<article>`/`<div>` →
**우클릭 → Copy → Copy outerHTML**

> ⚠️ `Ctrl+U`(페이지 소스 보기)로는 안 됩니다. 쿠팡 리뷰는 JS로 나중에 그려지므로
> 반드시 **DevTools의 Elements 패널**에서 가져와야 합니다.

진단 리포트는 이런 형태입니다. 리뷰 본문·작성자명은 `⟨text:N⟩` 으로 자동 마스킹되고,
URL의 쿼리스트링도 제거됩니다.

```
[리뷰 카드]
  article.sdp-review__article__list → 0개
  ⚠ 매칭된 selector가 없습니다 — 이 항목을 고쳐야 합니다.

[날짜로 보이는 텍스트]
  span.ReviewCard_date__z3  "2026.08.28"

[리뷰 카드 구조 샘플]
  (리뷰 카드 selector가 모두 실패해 날짜 요소의 조상으로 추정)
  div.ReviewCard_head__h1
    span.ReviewCard_author__y2  "⟨text:3⟩"
    span.ReviewCard_date__z3  "2026.08.28"
```

### 2단계 — selector 고치기

DOM selector는 **한 파일에만** 모여 있습니다.

```
extension/src/parsers/selectors.ts
```

1. 쿠팡 페이지에서 개발자도구로 상품 카드의 실제 클래스명을 확인
2. `PRODUCT_CARD_SELECTORS` / `NAME_SELECTORS` / `PRICE_SELECTORS` 등 해당 배열 **맨 앞**에 추가
3. `npm run build` 후 `chrome://extensions` 에서 확장 새로고침

### 리뷰 영역은 클래스가 아니라 앵커로 찾습니다

쿠팡은 2026년 개편으로 리뷰 영역을 Tailwind 유틸리티 클래스로 바꿨습니다.

```html
<article class="twc-pt-[16px] xl:twc-pt-[24px] twc-border-b-[1px] ...">
  <div class="twc-text-[14px]/[15px] twc-text-bluegray-700">2026.07.24</div>  <!-- 작성일 -->
  <div class="twc-text-[14px]/[17px] twc-text-bluegray-700">판매자: 쿠팡(주)</div>  <!-- 같은 클래스! -->
  ...
  <div class="sdp-review__article__list__help js_reviewArticleHelpfulContainer"
       data-review-id="956372574">  <!-- ← 유일하게 안정적인 앵커 -->
```

의미 있는 클래스명이 없고 작성일·판매자·옵션명이 같은 클래스를 공유하므로,
파서는 클래스 대신 **구조적 앵커**를 씁니다.

| 대상 | 방법 |
|---|---|
| 리뷰 카드 | `[data-review-id]` 앵커 → `closest("article, li, section")` |
| 작성일 | 요소의 **전체 텍스트가 날짜와 정확히 일치**하는 잎 노드 (본문 속 날짜 오인 방지) |
| 중복 제거 키 | `data-review-id` (없으면 작성일 + 본문 앞 80자) |

리뷰 날짜가 읽히지 않을 때도 같은 파일의 `REVIEW_ITEM_SELECTORS` / `REVIEW_DATE_SELECTORS` /
`REVIEW_ID_ANCHOR_SELECTORS` 를 수정하면 됩니다. 리뷰 카드 구조를 못 찾으면 날짜 패턴(`2026.08.15`)만으로 훑는 안전망이 동작하며,
이 경우 확장이 "값이 부정확할 수 있습니다"라고 경고합니다.

위 예시라면 이렇게 고칩니다.

```ts
export const REVIEW_ITEM_SELECTORS = [
  "div[class*='ReviewCard_root']",        // ← 새로 추가 (맨 앞)
  "article.sdp-review__article__list",
  ...
] as const;

export const REVIEW_DATE_SELECTORS = [
  "[class*='ReviewCard_date']",           // ← 새로 추가 (맨 앞)
  "div.sdp-review__article__list__info__product-info__reg-date",
  ...
] as const;
```

확장 popup은 어떤 selector로 카드를 찾았는지(`selector: li.search-product`) 표시하므로
어디가 실패했는지 바로 알 수 있습니다. content script 콘솔에도 제외 사유가 남습니다.

## 원칙

- 현재 Chrome 페이지에 **실제 노출된 데이터만** 수집합니다.
- DOM에 없는 값은 만들어내지 않습니다 (`null` 저장, UI에 `-` 표시).
- 조회수(`view_count`)는 데이터 원천이 없으므로 **항상 `NULL`** 입니다. 컬럼 구조만 준비되어 있습니다.
- 최근 30일 리뷰수는 쿠팡이 제공하지 않으므로 **유도**한 값이며, 실측인지 환산(추정)인지 화면에 명시합니다.
- 쿠팡이 표시하는 "한 달간 N명 구매" 문구는 **원문 그대로** 보관하며, 문구가 없는 상품은 `NULL`로 둡니다.
- 리뷰수 × 배수 값은 어디에서도 "실제 판매량"이라고 표기하지 않습니다.
- CAPTCHA / IP 차단 / 로그인 보호 / anti-bot 우회 기능은 **구현하지 않습니다.**
- 수집 실패 시 원인을 서버 로그와 브라우저 콘솔에 남깁니다.

## MVP 범위 밖 (아직 만들지 않음)

실제 판매량·조회수(쿠팡이 판매자 본인 상품 외에는 제공하지 않음), 전환율, Opportunity Score,
중국 1688 연동, 마진 계산, 무제한 대규모 크롤링, CAPTCHA·IP 차단·로그인 보호 우회.
